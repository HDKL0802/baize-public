# 跨端派活

白泽的后端跑在 NAS / 服务器上，**它看不见你电脑和手机上的东西**。
要在那些机器上做事，得把手伸过去 —— 也就是**派活**，而不是假装自己在本机。

## 一、先看有谁

`device_list` → 拿到 `devices[].id` / `online` / `caps`。

- **只给在线的派活**。离线设备的任务会**排队等它上线**（是等待，不是失败）——别急着重派，会堆一堆重复任务。
- 看 `caps` 判断这台机器**能不能干这件事**：能力不够的动作后端根本派不过去，别试。

## 二、再派活

`device_run`：

```json
{"deviceId":"desktop-xxx","action":"sys.info","args":{},"timeoutSec":120}
```

回执里的 `status` 有四种：`done` / `failed` / `rejected` / `timeout`。

### 只读档就能用的动作（免审批）

| 动作 | 用途 |
|---|---|
| `ping` | 探活 |
| `sys.info` | 这台机器的信息（主机名 / 系统 / 版本 / 能力） |
| `window.now` | 当前前台窗口 |
| `fs.stat` | 看一个路径的信息（存在 / 大小 / 修改时间），**不读内容** |
| `todo.list` | 手机端待办（只读） |

### 危险动作（`fs.delete` 一类）

会先走**人工审批**，而且要求那台机器**自己**放开了足够权限：

- 桌面端有**五档权限**：0 关闭 / 1 只读 / 2 只读指定目录 / 3 只读指定盘 / 4 完全访问。
  **闸门在设备侧判定** —— 权限不够的能力**根本不会上报**，所以不存在"我这边批了就能删"。
- 用户没放开就是没放开：**别反复重试**，把"要删什么、为什么、删错了会怎样"讲清楚，让他自己决定。

## 三、回复口径

- 说结果要带全三件事：**在哪台机器上**、**什么动作**、**`status`**。
- 失败就把 `error` 原文带回来，别含糊成"没成功"——原文里通常写着原因（权限不足 / 路径不存在 / 被驳回）。
- `timeout` **不等于失败**：那台机器可能只是睡着了。让用户确认它还醒着，再决定要不要重试。
- 一句话原则：**派活的过程本身就是结果的一部分**，如实转述，别替设备美化。
