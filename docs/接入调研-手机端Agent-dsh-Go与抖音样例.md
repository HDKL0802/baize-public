## 3. 形态判定

用户问的三类形态：

| 形态 | 含义 | dsh-Go 属于吗 | 依据 |
|---|---|---|---|
| (a) 把电脑上的 harness/网关搬到手机本地跑 | 整套引擎在手机里，离线也能跑工具 | **是，且是主形态** | README"运行在手机上的是 DSH 引擎"、官网"整套 DSH 引擎，就跑在这台手机里"、需 1 GB 本机环境 |
| (b) 手机当客户端连远端 | 手机只是壳，算力在电脑/服务器 | **是，次形态** | SSH / DSHarness Remote 两种连接方式，可"只连远程不装本机环境" |
| (c) 手机端自建 Agent 直接操作手机 UI | 无障碍/注入方式点按输入滑动 | **是，但受限且有版本冲突** | README 明确要求无障碍权限、Android 14+ 配 Shizuku/ADB；官网写"即将上线" |

**结论：dsh-Go 是 (a) 为主、(b) 并存、(c) 受限的"三合一"**，不是单纯的"手机客户端"。
它的 (c) 与"电脑上跑 ADB 去控制手机"是两条不同的执行路径：**决策与执行都在手机里**，不依赖电脑。

## 4. 与白泽现状的关系

### 4.1 白泽这边的事实（仓库内可查）

| 能力 | 现状 | 出处 |
|---|---|---|
| 设备中枢 | `/ws/device` 长连接 + hub 派任务 + 审批闸门，已有 | `docs/白泽功能切分与本地控制方案.md` |
| 桌面执行器 | gui/fs/shell/browser/window 已在跑 | 同上 |
| 手机执行器（ADB 主线） | **设计阶段，未落地**；文档里 ADB"未安装"、无真机连接记录 | `docs/白泽本地控制实施计划.md` T1.1–T1.6 |
| 无障碍增强 | 列为 **P3 可选**，`mobile/android` 现无 AccessibilityService | 同文档 P3 |
| 手机 App | `mobile/android`（bz-todo，WebView 壳 + 原生桥），有自己的 WebUI | 仓库现状 |

### 4.2 拓扑差异（这是判断"替代还是互补"的关键）

| 维度 | dsh-Go | 白泽 ADB 主线（计划） |
|---|---|---|
| 运行时在哪 | **手机** | **电脑**（Windows ADB 宿主） |
| 谁决策 | 手机里的 DSH 引擎 | 白泽后端 + VLM（autoglm-phone / glm-4.6v） |
| 需要的手机权限 | 无障碍；"不打扰"要 Android 14+ 且 Shizuku/自连 ADB | 开发者模式 + USB 调试 + RSA 授权 + ADBKeyboard |
| 屏幕来源 | 手机本机 | `adb screencap` 回到电脑 |
| 断网/离线 | 本机引擎可跑工具，但模型请求仍要出网 | 断网即不可用 |
| 与白泽协议 | 自有 DSH 协议（ds-harness-remote） | 白泽自有 `/ws/device` 协议 |

**判定：不是替代关系。** 两者跑在不同侧（手机 vs 电脑），解决的问题也不同。
真正的互补只在"**手机脱离电脑仍要干活**"这一段——那正是白泽 ADB 主线覆盖不到的场景。
但代价是：手机要装一整套运行时（约 1 GB）、要单独配模型、要维护第二套 Agent 逻辑。

## 5. 能不能融进白泽

### 5.1 明确不能做的两件

1. **把 dsh-Go 代码并进白泽主仓。**
   白泽 `LICENSE` 主体是 **MIT**（仅 OpenHuman 衍生目录例外为 GPL-3.0），dsh-Go 是 **AGPL-3.0**。
   把 AGPL 代码并入 MIT 主体，等于让整个组合分发受 AGPL 约束，与白泽现有授权承诺冲突。
   另外它的**名称、标识、吉祥物形象不在开源授权内**，不能再分发。
2. **把 dsh-Go 的 APK 打进白泽安装包。** 同上：再分发 + 商标/素材条款风险，且用户装的是"白泽"，里面却跑着第三方的完整产品。

### 5.2 可做的三档（工作量均为粗估，标"推测"）

| 档 | 做什么 | 前置条件 | 工作量（推测） | 风险 |
|---|---|---|---|---|
| **A. 设备层协议桥** | 白泽 hub 把手机上的 DSH 当成一种设备派活（对接 ds-harness-remote） | 拿到该协议的文档或实测抓包；确认它的调用粒度 | **1–2 周**起，协议不清则不确定 | 两套 Agent 运行时职责重叠，出问题难归因；协议若只面向 DSH 客户端，白泽接进去会很别扭 |
| **B. 白泽自建手机执行器** | 在 `mobile/android` 加 AccessibilityService（+ Shizuku 可选），走白泽自己的 `/ws/device`，做 observe/act/Take_over | 一台 **Android 12+** 真机；无障碍授权引导；截图与坐标归一化 | **3–4 周**（推测），与既有 P3 重叠 | 与 ADB 主线重复造轮子；厂商 ROM 差异大 |
| **C. 只登记为「外部 Agent」** | 不接 UI，只在白泽里登记"手机上的 dsh-Go"，由人手动派活/看结果 | dsh-Go 得暴露可被外部调用的 HTTP/命令入口——**未核实** | 界面 0.5–1 周；真实能力取决于对方接口 | 大概率只能"人去用"，白泽调度不进去 |

### 5.3 建议

- **短期不做 A**：协议没拿到，属于"先花两周再决定要不要花两个月"。
- **B 不要新开线**：白泽已有 P3 无障碍增强的口子，等 ADB 主线（T1.1–T1.6）先在真机上跑通，再决定要不要上无障碍。否则两条手机路线会互相抢维护成本。
- **C 只做文档/登记位**：不写代码也能落地，且不引入许可风险。
- **一句话**：dsh-Go 值得"看思路"（它证明了手机本地跑整套 harness + 无障碍操控这条路能走通），但不适合"搬进白泽"。

## 6. 需要用户拍板的三件事

1. 是否接受"白泽不做手机本地运行时、坚持电脑侧执行器"这个定位（默认建议）。
2. 是否愿意为手机执行器准备一台 **Android 12+ 真机**（B 档和 ADB 主线都卡在这；现在仓库里连 `adb` 都没装）。
3. 是否允许白泽仓库出现 AGPL 目录（**不推荐**，会污染 MIT 授权承诺）。
