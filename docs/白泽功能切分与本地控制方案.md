## 0. 结论速览

1. **不需要「全部切」**：项目真正的耦合点在 `agentrt / agentsvc / llm / tools / store / hub`，这几个必须同进程；其余按 8 个可独立单元 + 3 类本地执行器收敛。
2. **桌面 GUI 控制已有一半底座**：设备中枢（`/ws/device` + `hub` + 审批）与 `gui.screenshot/click/input/key` 已在跑，方案是"补原语 + 改决策回路"，不是从零建。
3. **手机 GUI 控制是空白**：`mobile/android` 只有 8 个 Java 文件，无无障碍、无 ADB 通道；必须新建执行器。
4. **AutoGLM 可集成，但只提供「决策」，不提供「执行」**：官方开放平台有 `autoglm-phone` 模型 API + 开源 `zai-org/Open-AutoGLM`（Apache-2.0）框架，执行端仍是你自己的 ADB 客户端。**【核实】**
5. **豆包手机固件逆向判定：不可做，做了也没用**：无公开固件 dump，且系统级注入依赖厂商签名权限，非 root/刷机可得。**【核实（负向）】**
6. **本机不能跑本地视觉模型**：GT 730 / 1 GB 显存；视觉决策必须走云端 API。

| # | 问题 | 结论 | 等级 |
|---|---|---|---|
| 1 | 产品形态 | **三种并存**：①消费级 AutoGLM App（iOS/安卓 `com.zhipu.agent`）= 云端手机/云电脑，用户只用 App；②开放平台模型 `autoglm-phone`（`open.bigmodel.cn/api/paas/v4`）= 供第三方程序调用的**决策 API**；③开源 `Open-AutoGLM`（代码 Apache-2.0 + 权重 `AutoGLM-Phone-9B` MIT）。**不是"仅自家 App 使用"，但也绝不等于"一个 API 就能控制手机"** | 核实 |

| 4 | 计费与限制 | 平台按量计费（元/百万 tokens，输入/输出分档、含缓存计费）；**定价表未单列 `autoglm-phone` 单价 →【未找到】**；"限时免费"仅见第三方教程表述 →【待验证】；RPM/TPM 限流无公开说明 →【未找到】 | 部分核实 |
| 5 | 与豆包差距 | 见下表 | 核实/二手混合 |

### 2.1 AutoGLM vs 豆包手机助手

| 维度 | AutoGLM（开放/开源路线） | 豆包手机助手 |
|---|---|---|
| 权限层级 | 普通 App 级：ADB shell（`input`/`screencap`）或无障碍 | **系统级**（媒体转述使用 `INJECT_EVENTS` 系统权限），操作系统层集成 |
| 跨应用 | 能，但每个应用都靠像素识别，慢 | 能，且可调用系统服务，路径更短 |
| 免授权 | 不能（每次换机都要开发者模式 + 授权） | 消费者开箱即用 |
| 受限场景 | `FLAG_SECURE` 页面黑屏；锁屏/支付/验证码需 Take_over 人工接管；输入法需额外装 ADBKeyboard | 报道称可跨应用执行复杂任务，系统 UI 也在控制面内 |
| 可编程性 | **强**：API + 开源框架 + 可自托管 | **无对外 Agent API**，三方接入走 SAEP "声明"协议 |
| 结论 | 适合"自己有设备、要可编程、可审计"的个人智能体 | 适合"开箱即用"，但**不可集成进白泽** |

> 方案定调：**手机控制以 AutoGLM 的"决策模型 + 自建 ADB 执行器"为基线**，豆包不作为可集成目标。

## 3. A. 功能切分结论

**回答"是不是把所有能切的功能全部单独切出来"：不是。**

切分粒度四条原则：

1. **按能力域切，不按 UI 按钮/页面切**——UI 是视图层，切它只会把同一份状态拆到两处。
2. **按信任边界切**：凡碰"注入、文件写、命令执行、设备控制"的能力，必须独立成可被闸门管控的执行器。
3. **按故障域切**：会崩、会卡、会吃资源的（浏览器、语音、插件、通道）独立进程；崩了不能拖垮编排主循环。
4. **同进程判据**：共享内存状态 + 高频调用 + 同一权限域。`agentrt`（主循环）→`agentsvc`（服务门面）→`llm.Router`→`tools.Registry`→`store`（SQLite 单写）是一条指针级调用链，**拆成进程只会带来序列化开销与一致性问题**。

### 3.1 能力域清单

| 能力域 | 可否远程 | 是否必须本地 | 依赖 | 优先级 |
|---|---|---|---|---|
| 编排 / Run 主循环（agentrt、agentsvc、agent_runs） | 是（HTTP/WS） | 否 | llm、tools、store | P0（**同进程**） |
| 模型路由（llm：providers、vision、embedding） | 是 | 否 | 各家 API / 本地模型 | P0（同进程） |
| 工具注册与技能（tools、skills、mcp、slash） | 是 | 否 | 各执行器 | P0（同进程） |
| 记忆 / 笔记（memory、notebook、notes API、graph） | 是 | 否 | SQLite + Obsidian vault | P0（同进程，vault 可外挂） |
| 任务与设备中枢（hub、store/task、approvals） | 是 | 否 | `/ws/device` 长连接 | P0（**同进程**，会话状态） |
| 桌面执行器（Gui/Fs/Shell/Browser/Window） | 仅本机回环 + 中枢 | **是** | Win32 / UIA / Chrome | P0 |
| 手机执行器（ADB / 无障碍） | 是（中枢下发） | **是**（在手机上/本机 ADB 宿主） | adb、ADBKeyboard、VLM | P0 |
| 浏览器自动化（browser.* + CDP + 扩展） | 是 | **是**（本机 Chrome） | 浏览器实例 | P1 |
| 语音（voice：stt/tts/translate） | 是 | 否（可云端） | 模型 / 本地引擎 | P1（可独立服务） |
| 知识库（kb：files/state/stats/op） | 是 | 否 | 文件存储 + 嵌入 | P1（可独立服务） |
| 消息通道（channels：飞书/钉钉/微信类/小易等） | 是 | 否 | 各平台回调 | P1（独立网关） |
| 定时 / 钩子（cron、hooks、heartbeat） | 是 | 否 | store | P1（可独立） |
| 账户 / 分组 / 通话 / 冲突（accounts、calls、conflicts） | 是 | 否 | store | P2 |
| 插件市场 / 人设 / 分享（plugins、persona、sharing） | 是 | 否 | 网络、文件 | P2 |
| 备份 / 回滚 / 观测（backup、checkpoints、logx/observe） | 是 | 否（备份目标可远端） | 文件系统 | P2 |

**收敛结果**：34 个 internal 包 → **8 个可独立部署单元**（编排核心、模型网关、知识库、语音、通道网关、定时器、插件宿主、备份/观测）+ **3 类本地执行器**（桌面、手机、浏览器）。对外统一 `/v1/*` 契约，旧 `/api/agent/*` 保留为兼容层（不新增调用方）。

## 4. B. 本地电脑控制（Windows GUI）方案

### 4.1 架构

```
后端(agent) ── /ws/device ──► desktop 执行器(本机) ──► Win32 / UIA / GDI
      │                          ▲
      └─ 审批闸门(approvals) ─────┘   本机三重闸门：开关 + 进程白名单 + 逐次审批（已实现）
```

复用现有 `hub`（任务 + 审批 + 超时 + 回执）与 `proto.knownActions`，**不新建通信层**；只补动作与决策回路。`/api/local/*` 继续只对本机回环开放。

### 4.2 动作原语（★=需新增）

| 原语 | 参数 | 说明 |
|---|---|---|
| `gui.screenshot` | monitor/region | 已有；回本地 PNG 路径，不回 base64（省带宽） |
| `gui.click` | x,y,button,clicks | 已有 |
| `gui.input` | text | 已有，Unicode 逐码元，中文可用 |
| `gui.key` | combo | 已有，支持 `ctrl+s` 组合 |
| ★`gui.move` / ★`gui.drag` | 起止点 | 拖拽、悬停 |
| ★`gui.scroll` | dx,dy,unit | 滚轮（页/行） |
| ★`gui.window` | list/focus/resize/close | 窗口枚举与激活，用 `window.now` 同一套 HWND 口径 |
| ★`gui.wait` | cond(窗口标题/像素/空闲) | 显式等待，替代盲目 sleep |
| ★`gui.assert` | 期望窗口标题/像素签名 | 断言，决定是否算成功 |
| ★`ui.tree` | depth,filter | UIA 控件树（见 4.3） |

### 4.3 视觉决策：UIA 优先，VLM 兜底

- **先 UIA**：`IUIAutomation` 取控件树（Name/AutomationId/BoundingRectangle/IsEnabled），能精确点到控件，成本几乎为零；但自绘界面、Electron/CEF、游戏窗口常无节点 **【核实：公开文档与常见实践】**。
- **再 VLM**：UIA 找不到目标时，截该窗口 → 云端 `GLM-4.6V` 返回归一化坐标 + 动作；**本机 GT 730 无法本地推理**，这是硬约束。
- 折中：UIA 拿到候选控件 → 只把候选区域截图给 VLM 复核，省 token。

### 4.4 截图与坐标映射（DPI 坑）

现状：进程**未声明 DPI 感知**，`SetCursorPos`、窗口矩形、截图三者都在系统虚拟坐标系，闭环自洽；1920×1080@96DPI 下 1:1。风险点：

1. 一旦改成 Per-Monitor V2，`GetWindowDC` 截到的是**物理像素**，而 `SetCursorPos` 用**物理坐标**，两套口径必须同时切换，否则点偏。
2. 存在 2 块虚拟显示适配器（GameViewer / MuMu）：`GetSystemMetrics(SM_CXSCREEN)` 与"当前截图所在显示器"可能不一致 → **截图必须带显示器枚举**（`EnumDisplayMonitors`），不要只用主屏。
3. 与模型交互时统一传 **0–1 归一化坐标**，由执行器按"该截图所属 monitor 的 rect + scale"还原为像素，避免模型侧被分辨率污染。

### 4.5 失败重试与幂等

| 动作类型 | 重试 | 策略 |
|---|---|---|
| 只读（截图/窗口/UIA） | 3 次，指数退避 100/300/900 ms | 失败只上报，不重派 |
| 可重复写（focus/resize/scroll） | 2 次 | 每次前重新读状态 |
| 不可逆（click/input/drag） | **0 次自动重试** | 改为"执行→回读截图→断言→再决定" |
| 超时 | 单动作 3 s，单任务 60 s | 超时 kill 并回执 failed，不静默 |

失败分类必须落地：`no_target`（UIA 无节点）、`blocked`（被 UAC/高完整性窗口拦截，UIPI）、`timeout`、`perm_denied`（闸门拒绝）。**不允许"看起来成功其实没点到"**。

### 4.6 安全边界（在现有三重闸门之上补 4 条）

1. **动作分级**：只读（screenshot/window list）→ 写入（click/input/scroll）→ 危险（sys.exec/fs.delete）三档，闸门按档收紧。
2. **UIPI 现实**：管理员权限窗口收不到普通进程注入，必须提前提示"需提权"或直接拒绝，**不要假装能点**。
3. **敏感窗口黑名单**：UAC 弹窗、凭据输入框、银行/支付类进程一律拒绝自动输入（宁可 Take_over）。
4. **二次确认**：危险动作先回一张"目标窗口截图 + 将执行的动作"给用户确认；全链路审计（谁、何时、哪个窗口、什么动作、结果）。

## 5. C. 手机控制（Android）方案

### 5.1 路线选择：ADB 主线 + 无障碍增强（混合，不是二选一）

| 维度 | ADB + 截图 + VLM（**主线**） | AccessibilityService（增强） |
|---|---|---|
| root | 不需要 | 不需要 |
| 授权 | 开发者模式 + USB 调试 + RSA 授权（无线调试需配对码） | 设置里手动开启 |
| 信息 | 纯像素（+ 可选 `uiautomator dump`） | 节点树（文本/控件精确） |
| 延迟 | 每步 1–3 s【待验证】 | 低 |
| 硬伤 | `FLAG_SECURE` 黑屏；中文输入需 ADBKeyboard | 厂商省电查杀；Android 14 截屏需前台服务且每次授权 |

选 ADB 主线的**决定性理由**：与 AutoGLM 官方路线同源（同一套动作空间、同一个模型），能直接复用 `Open-AutoGLM` 的 prompt 与动作 schema；无障碍作为二期增强，写在自有 App 内（`com.baize.todo` 目前无该能力，需新增 Service 与用户手动授权）。

### 5.2 执行器命令清单（本机 Windows 侧宿主）

| 能力 | 命令 |
|---|---|
| 设备 | `adb devices -l`（型号/序列号/连接方式） |
| 截图 | `adb exec-out screencap -p > shot.png`（或 `screencap -p /sdcard/s.png` + `pull`） |
| 节点树 | `adb shell uiautomator dump /sdcard/ui.xml` + `adb pull` |
| 点击 | `adb shell input tap x y` |
| 滑动 | `adb shell input swipe x1 y1 x2 y2 [ms]` |
| 文本 | `adb shell input text 'abc'`（ASCII）；中文走 ADBKeyboard：`am broadcast -a ADB_INPUT_TEXT --es msg '...'` |
| 按键 | `adb shell input keyevent 3/4/187`（Home/Back/Recents） |
| 启动应用 | `adb shell monkey -p <pkg> -c android.intent.category.LAUNCHER 1` 或 `am start -n <pkg>/<activity>` |
| 当前界面 | `adb shell dumpsys window \| findstr mCurrentFocus` |
| 无线连接 | `adb pair <ip>:<port> <code>` → `adb connect <ip>:<port>` |
| 分辨率 | `adb shell wm size` / `wm density`（坐标换算依据） |

坐标同样用 0–1 归一化：截图实际像素（`wm size`）× 归一化值 → `input tap`；分辨率变化（折叠屏/分屏）必须每次重取。

### 5.3 接哪个视觉模型

| 选项 | 适用 | 结论 |
|---|---|---|
| `autoglm-phone`（智谱开放平台） | 与 Open-AutoGLM 动作空间同源，开箱即用 | **首选**（API 调用，按量计费，单价【未找到】） |
| `GLM-4.6V` | 自建 prompt、需要 function calling 与长上下文 | 备选/复核 |
| 本地 `AutoGLM-Phone-9B` | 隐私优先、离线 | 本机 **不可行**（GT 730）；需 ≥16 GB 级显存的独立 GPU 【待验证具体门槛】 |

### 5.4 无 root 可行性 & 与豆包的差距

- 无 root **可跑通**：ADB shell 的 `input`/`screencap` 由 `shell` 用户执行，足够点击与截图；缺的是系统级能力（见 2.1）。
- 与豆包的真实差距不是"模型聪明程度"，而是**权限层级**：豆包在操作系统内（可调系统服务、免授权），我们在系统外（ADB 注入/无障碍），因此在锁屏、支付、`FLAG_SECURE` 页面、需要厂商签名的场景必然打不过；这些场景的正确做法是 **Take_over 人工接管**，而不是硬闯。

## 6. D. 豆包手机固件逆向可行性判定

**结论：不可做；即使做了也没有产品价值。**

| 判据 | 事实 | 等级 |
|---|---|---|
| 有没有固件 | GitHub 搜 `nubia M153` 仓库 0 条；努比亚官方 ROM 列表无 M153/NaviX 机型 | 核实（负向） |
| 有没有社区成果 | 仅有系统软件字符串解包（发现 smartisan 痕迹）与黑盒进程分析（aivoice/assistantaiagent/aikernel）；**未找到公开固件 dump** | 核实 |
| 逆向能拿到什么 | 系统级 Agent 的能力依赖**厂商签名权限**（媒体转述为 `INJECT_EVENTS` 级系统权限）。拿到代码也没有签名，装不进、跑不了 | 核实+二手 |
| 刷机通道 | 媒体报道"几乎没法用 ROM 包刷机"；且该助手"不是一个普通 APK 能搞定" | 二手 |
| 已有开源替代 | `open-doubao-phone`、`android-use` 属**重实现**，不是固件逆向 | 核实 |

**替代路径（推荐）**：
1. 用 `Open-AutoGLM` + 自建 ADB 执行器，把"跨应用任务"做到 70–80% 场景；
2. 用 `Take_over` 兜住登录/验证码/支付等必须人工的环节；
3. 想要"豆包级体验"只有一条合法路：**买一台 NaviX Ultra 当对照机/体验机**，而不是逆向它。

## 7. E. 法律与风险（非法律意见）

| 风险 | 说明 | 建议 |
|---|---|---|
| 闭源软件逆向 | 反编译/解包闭源客户端可能触及著作权与反不正当竞争；"为兼容而逆向"的边界在国内司法实践中并不宽松 | 只做**互操作必需的最小观察**（网络协议、公开 API），不复制代码、不绕过技术措施 |
| 固件提取 | 提取/重打包固件通常涉及规避技术保护措施与厂商授权 | **不做**（本方案 D 节已否） |
| 模型 API 条款 | 转售、批量代调用、把输出用于训练他模型，通常被 ToS 禁止；`autoglm-phone` 的商用与限流条款需以官方为准 | 上线前逐条比对 ToS；保留调用凭证与用量记录 |
| 开源许可混入 | 仓库根同时存在 `LICENSE` 与 `LICENSE-GPL-3.0.txt`，与文档声明的 MIT 存在冲突风险 | **先做许可审计**，明确每个目录的许可，GPL 代码不得并入 MIT 主体 |
| 公开仓发布 | `baize-public` / Gitee 公开镜像存在密钥泄漏、设备控制能力被滥用的风险（GUI/ADB 执行器一旦被远程调用即是后门） | 公开仓只放**不含执行器与凭据**的构建；执行器默认关闭且强制本机开关 |
| 设备控制合规 | 自动点击/输入在金融、医疗、政务类应用可能违反其用户协议 | 敏感应用加入黑名单，默认拒绝 |

## 8. F. 分阶段实施计划（先竖切，再横向复制）

| 阶段 | 目标 | 产出 | 验收标准 | 依赖 |
|---|---|---|---|---|
| **P0 桌面竖切**（1 条链路跑通） | 记事本/浏览器上完成"截图→决策→点击→回读"闭环 | 新增 `ui.tree / gui.wait / gui.assert`；VLM 兜底回路；失败分类 | 3 个任务各跑 10 次，成功率 ≥ 80%，失败必带原因码，无"假成功" | 现有三重闸门；云端 `GLM-4.6V` Key |
| **P1 手机竖切** | 用 ADB 在真机上完成"打开应用→搜索→点击结果" | 手机执行器（screencap/input/am/monkey）+ 归一化坐标 + `autoglm-phone` 决策 + Take_over | 真机 3 个任务各 5 次，成功率 ≥ 60%（首版允许人工接管）；`adb devices` 可见、无 root | 装 platform-tools；一台测试机；API Key |
| **P2 能力域 API 化** | 把 100+ `/api/agent/*` 收敛为 8 单元 + `/v1/*` 契约 | OpenAPI 描述、域边界文档、兼容层、鉴权统一 | 旧路径全绿；新契约覆盖 P0/P1 全部动作；无跨进程共享状态 | P0/P1 完成（动作集稳定才值得固化） |
| **P3 无障碍增强（可选）** | 自有 App 内加 AccessibilityService，节点树优先 | Service + 授权引导 + 事件流（界面变化订阅） | 同任务在节点树通道下延迟显著低于 ADB 通道；可回退 | P1；安卓工程改造能力 |
| **P4 横向复制与安全收口** | 把"桌面/手机"同一套原语复用到浏览器、Linux 桌面 | 执行器 SDK 抽象、审计与回滚、敏感应用/窗口黑名单 | 三类执行器同一份协议；审计可回放；危险动作二次确认 100% 生效 | P0–P3 |

排序理由：P0 验证"模型决策 + 本地执行"这条**最不确定的价值链**；P1 才验证"跨设备"；API 化放 P2 是因为**动作集不稳定时固化接口等于返工**。
