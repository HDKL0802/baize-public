# 白泽多生态插件接入 · 设计（0.8.2 起）

> 目标（用户 m04902）：白泽内置多种插件方式，把 **DSH / Trae 等各 Agent 生态的插件市场**都接进来，
> 让白泽瞬间拥有大生态库。参考实现：**DSH Market**（`@deepseek-ai/dsh-plugin-market`，开源、用户实测最好用）。

---

## 一、两边的协议对比（实测结论）

| 维度 | 白泽现状 | DSH Market |
|---|---|---|
| 源定义 | `plugins.Source{Name,URL,Enabled}` | `indexes: string[]`（http(s) URL 列表） |
| 索引 | `index.json` = `{schema,name,updated,plugins:[Meta]}` | **格式 1**：`{format:1,title,description?,metadata:{categories,labels,sortKeys},plugins:[MarketPlugin]}` |
| 插件条目 | `Meta{id,name,version,description,author,homepage,license,tags,minBaize,channel,stage,category,url,sha256,size}` | `MarketPlugin{name,title?,description?,icon?,author?,homepage?,repository?,metadata:{category?,keywords,labels,sortKeys},versions:[MarketVersion]}` |
| 版本 | **没有版本概念**（一条插件一个包） | `versions[]` 每版有 `version/publishTimestamp/source{npm\|git}/engines{dsh}` |
| 安装单位 | `.zip` 包（`plugin.json` + `skills/<slug>/SKILL.md` + 可选 `mcp[]`） | **cordis bundle**（npm 包或 git+commit），装的是 DSH 运行时插件 |
| 落点 | 技能目录 + 注册 MCP | cordis fiber 挂载到宿主进程 |

**关键结论（不可回避）**：两边的**插件本体**不通用 —— 白泽要的是「技能包（SKILL.md）+ 可选 MCP 服务」，
DSH 装的是 cordis 运行时插件（依赖 `@deepseek-ai/cordis` ^4.0.1，靠 fiber 挂载）。
**把 DSH 的 cordis bundle 塞进白泽不会跑起来**（没有 cordis 宿主）。

所以「生态接入」要分两层做，第二层才是真生态：

## 二、两层设计

### 第一层：白泽直接吃 DSH 格式的市场索引（索引即目录）

- 白泽新增一个**源适配器**：`dsh-market` 型源，索引不是白泽的 index.json，而是 DSH 的格式 1 文档。
- 拉到的每条 DSH 插件映射成白泽货架条目：
  - `name` → `Meta.id`（DSH 的 npm 包名，含 `@scope/` 时按白泽 id 规则归一）
  - `title/description` → `Meta.name/description`
  - `repository.url` → `Meta.homepage`
  - `versions[0].version` → `Meta.version`
  - `metadata.category/keywords/labels` → `Meta.category/tags`
  - `channel` 固定 `community`（**DSH 插件一律不宣称官方**）
  - `stage` 按版本号判：`>=1.0.0` → stable，否则 beta
  - `Meta.url` = 空 + 新增 `Meta.install` 字段（描述 DSH 侧安装参数，**白泽不执行**）
- 界面明确区分：**「可装到白泽」**（白泽原生包）vs **「仅目录 · DSH 生态」**（只展示、
  安装跳转到 DSH 侧或复制安装命令）。—— 这一条是**诚实边界**，不做「看着能装其实装不了」。

### 第二层：生态插件的能力转译（真生态，核心工程量）

对 DSH/Trae 生态插件，按内容分四类，各有落法：

| 插件内容 | 判定 | 白泽落地方式 |
|---|---|---|
| 含 `skills/*/SKILL.md` 或 `.claude/skills` | 技能型 | **直接转成白泽技能**（SKILL.md 本身就是通用格式），装进白泽技能目录 |
| 只提供 MCP server（stdio/http） | 工具型 | 在白泽 `plugin.json` 里写 `mcp[]` 段，白泽按自己的 MCP 管理器注册 |
| 只提供提示词/规则/工作流（markdown） | 提示型 | 转成白泽 skill（SKILL.md 带 description） |
| 纯 cordis 运行时（UI/面板/hook） | 运行时型 | **白泽不接**（无 cordis 宿主）；目录里只展示来源与说明 |

实现落点：新增 `agent/internal/plugins/ecology/` 包 + 一个 `tools/dsh-market-sync` 脚本：
1. 拉 DSH 格式 1 索引（HTTP GET，缓存 + sha256 记录）
2. 逐条判定上面的四类
3. 技能型/提示型 → 生成白泽技能目录（SKILL.md）
4. 工具型 → 生成 `plugin.json`（含 `mcp[]`）+ zip
5. 产出白泽格式 `index.json` + `packages/*.zip` → **挂成一个普通白泽插件源**

这样 DSH 生态的插件就**真的能在白泽里用**，而不是只列个名字。

## 四、边界（如实）

1. **纯 cordis 运行时插件接不了**（白泽没有 cordis 宿主）——只做目录展示，不假装能装。
2. DSH 插件装的是 npm/git 包，白泽装的是 zip+SKILL.md —— **转换的是「内容」，不是「包」**。
3. 每个插件能否转，取决于它的内容形态；四类判定规则写在上表，判定结果逐条如实显示。
4. 第三方插件的**安全性**由用户自己判断（目录里显示仓库地址与许可证，不代替用户决策）。

## 五、实施顺序

1. `plugins/ecology` 包：DSH 格式 1 索引解析 + 四类判定 + 生成白泽包与 index.json。
2. 后端接口：`GET /api/agent/ecology/dsh`（同步结果）+ `POST /api/agent/ecology/dsh/sync`。
3. 桌面端「插件市场」页加「生态源」分组：DSH 生态 / Trae 生态 / 白泽原生。
4. 打通：把生成的 index.json + packages 挂成一个白泽源，`config.PluginSources` 指向它。
5. 测试：单测（解析四类判定）+ 端到端（拉真索引 → 生成 → 装一个技能型插件）。
